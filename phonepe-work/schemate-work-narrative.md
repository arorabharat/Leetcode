# PhonePe: building Schemate, the schema and data governance platform (work narrative)

This is a story-bank document, written to be narrated rather than read section by section. It captures everything I know about the work. Phrases marked *(Confluent)* are concepts from Confluent Schema Registry that I studied and borrowed from; they are worth confirming against what was actually built. Anything I'm unsure about is collected as open questions at the end of the chat conversation, not guessed here.

---

At PhonePe I work in the observability pod, and the biggest thing I've been building there is a schema governance and data governance platform called Schemate. To explain why it matters, you have to start with the scale. PhonePe pushes billions of events every day, and at any given moment around a million events are being generated every second or so across the system. Those events are pushed into a wide range of services, and hundreds of downstream services depend on them. Some consume them for payments flows, some for analytics, some for marketing and recommendations. Because PhonePe is a payments and fintech app, the availability standards are very strict. That combination is what makes the problem dangerous: a single incorrect schema, or one malformed event, can start failing downstream services, and with hundreds of consumers, a small mistake by one producer can spread quickly.

So the problem we set out to solve was how to let producers and consumers evolve their schemas independently, while still guaranteeing that the data passed between them follows the agreed schema and any other data constraints that either the producer or the consumer has enforced. On top of correctness, there was a discoverability problem. People who needed to build a use case on top of events had no good way of finding the appropriate event, so the platform also needed to give visibility into what events exist and what they contain.

The goal I set for Schemate was simple to state: any event that gets published must be validated against a schema, and that schema must be managed. And it had to be a self-service platform. We are an infra team, and if every schema change or onboarding needed us in the loop, we would become the bottleneck for every other service. So self-service, with the governance built into the workflow itself, was a hard design principle.

The first functional requirement was a schema storage system, essentially a schema registry, that stores the schemas. Teams could in principle define their schemas in several ways, and one of them is through code, which turned out to be the crux of the design. The industry-standard practice is schema-first: people write schema files, such as Avro or Protobuf definitions, and generate their data models from those files. Those generated models are what get used to send data across event systems. But our situation was the reverse. The code already existed. We had a hundred-plus services, with their event classes already written in Java, in production, serving payments traffic. Manually writing schemas for all of those services was not feasible, and neither was migrating them from Java classes to a schema-based toolchain. Even if it had been technically possible, convincing that many service teams to take that risk, on production payment paths, was not easy. So we had to build it the other way around: figure out how to generate the schema from the code that already existed, without adding much onboarding effort on the client side.

There were two approaches on the table. The first was to build it at runtime. Whenever a class is created or an event is published, we would determine the schema at runtime, cache it, and validate all events against it. Leadership was more aligned with this approach, and I understood why: it requires essentially zero effort from client teams. They could simply start calling our API to publish their data, and we would take on the work of validating it, registering the schema in our schema registry, and making sure no incorrect data got through.

I was against it, and I argued against it strongly. My concern was that it would make us the central bottleneck for the entire ecosystem. At this scale, with a million events being generated at a time, every event would pass through a system that we own, and anything that goes wrong at runtime is hard to mitigate quickly. For a payments company with strict availability requirements, putting a new system in the hot path of every event felt like the wrong risk to take.

So I proposed an alternative: a Maven plugin that captures the schema at build time and checks compatibility against the existing schemas. As a client, a team would add annotations on top of their classes. The plugin scans those annotated classes during the build, extracts the schema of each class, and registers it, and at build time itself it runs the compatibility check against what already exists in the system. Clients can set the compatibility level, backward, forward, or full, so that any existing consumer using a schema is guaranteed not to break after a change is published. *(The compatibility modes and the idea of a per-subject compatibility setting come from Confluent Schema Registry.)*

The philosophy behind my proposal was to shift left. The client who publishes the event should own the schema. If they generate an incorrect or incompatible schema, they should fail fast, and the earliest possible moment to tell them that their change would break an existing consumer is the build. That is much better than finding out in production. There was a second argument as well. If we built a central library or a central service that validates every event, all that CPU cost would land on a single system, and we would have to scale it for peak event volumes. With the build-time approach, each producer or consumer spends its own CPU cycles, so there is no central scaling problem for peak traffic. And there is a third benefit, which is isolation. If a service deploys an incorrect schema or makes an incorrect change, it does not impact other clients. The failure stays inside the team that made the change, rather than turning into an ecosystem-wide incident.

The platform also had to solve use cases beyond the basic producer and consumer problem. One was sending data to external parties. Whenever somebody publishes data that is going to an external party, there is a requirement to follow a strict schema and to make sure we are not sending any critical data. That data has to be masked. At that time there was no common service that let teams manage such rules, meaning how to mask the data and what transformation to apply before it goes to an external party. All of that was missing, so as the infra team we had to build it for the other services. A second use case came from services like the recommendation engine, which pulls recommendations, and the marketing team, who create banners. Sometimes they would put invalid data into a widget, so we also had to validate that the data adhered to the schema for those cases. That meant the platform was not only about Kafka-style producers and consumers; it was a general way of defining and enforcing what valid data looks like.

Before building, I investigated what already existed. I found a similar platform, Confluent Schema Registry, which is used to publish schemas for producers and consumers in the Kafka ecosystem. I spent around a month studying how the whole ecosystem works, and then took the learnings that applied to us. The ideas I took from it include subjects and versioned schemas, per-subject compatibility modes, and keeping the registry as a separate component rather than putting it inside the data path. *(Confluent: a subject is the scope in which a schema evolves; each subject has an ordered list of versions and its own compatibility setting; compatibility can be backward, forward, full, or transitive, where transitive checks against all earlier versions. Schemas get globally unique IDs that producers embed in messages and consumers use to fetch the schema; the registry lives outside the brokers and clients cache schemas.)* What I built on top of those ideas was different in an important way: the schema comes from annotated code at build time, and there is a governance workflow around every change.

Here is how that end-to-end flow works. The Maven plugin extracts all of the annotated classes and generates their schemas. The registration happens as part of the merge request to the develop pipeline. At the time of the merge request, before it is even ready to merge, the system ensures compatibility against the existing schemas. There is also an approval workflow built in. Any change that goes through needs to be manually approved by somebody, so the system generates a change set request. The owners of the downstream schemas, or the consumers affected, can review that change set and approve it. Once it is approved, the schema is published. Both of those steps, the compatibility check and the approval, need to happen before the deployment. So for any merge request raised into the develop pipeline, we generate the change set, run the compatibility check, and raise an approval workflow request. Once the approval comes through, we atomically apply all the changes in the change set, and only then can the merge request be merged into the system. As soon as the deploy happens, all of the schemas in it are activated.

The reason this design holds together is that it gives governance without becoming a bottleneck. Producers own their schemas and find out immediately if they are breaking someone. Consumers get a say through the approval step, so they are protected from surprise changes. The infra team does not sit in the middle of every change, and the platform stays out of the runtime path of payment events. That is why I consider this the most complex project I have worked on: it combines a scale and availability problem, a migration constraint that ruled out the textbook solution, a real disagreement about architecture that I had to resolve with leadership, and a workflow that has to be correct across hundreds of services.
